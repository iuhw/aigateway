## 结论

- 网关单请求基线开销 p50 0.475 ms；启用全部 7 个本地插件后增加 +0.064 ms/请求。
- M4 可观测插件（usage-report + otel-export）在全链之上增加 +0.062 ms/请求（otel 按出厂默认 BatchSpanProcessor + 丢弃导出器口径，span 即弃无保留，不含网络；与生产请求路径一致、不含网络；相对上一版全链 p50 增幅 +11.5%，门槛 <10%）。
- M5（prompt-template 注入 + canary 切流）在 M4 全链之上增加 +0.039 ms/请求（相对 M4 全链 p50 增幅 +6.5%，门槛 <10%）。
- 流式 TTFT 开销：+0.814 ms。
- 故障转移：冷却稳态与基线持平；强制每次重试+切换的开销来自配置的退避时间（10ms），网关自身开销毫秒级。
- 精确缓存命中略快于转发路径；上游为真实大模型（秒级延迟）时收益为秒级。
- 语义缓存命中路径 p50 0.543 ms（含进程内 mock embed 步骤；真实部署需另加 embed 网络往返）。
- webhook 审核路径 p50 28.758 ms（本地 stub allow。该数值主要是同进程 HTTP 客户端往返的事件循环开销——顺序纯客户端实测约 3ms/次、并发 8 约 16ms——插件自身网关侧开销可忽略；审核服务独立部署时另加网络往返与服务处理耗时）。
- 并发 8→64 RPS 下降源于单进程 Python GIL 与事件循环争用；生产部署可用多 worker 横向扩展。
